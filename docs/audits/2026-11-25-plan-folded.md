## Findings

### 1. max_shortfall bounds only how far output trails; both carried decimators LEAD (ceil(n/M) outputs), and steady<>'s FIFO and fed_by's staging are then undersized: silent wrong audio again

- **Lens:** change (The fold-in: every finding answered, nothing contradicted)
- **Where:** D35; section 3.2 (input_group, max_shortfall rows: '1/2 for a decimator by 2'); section 4 (max_shortfall composition, steady<>); section 6.1 (fed_by_workspace 'sized ... by the chain's ratio and shortfall'); sketch.h steady (k_capacity, line 907) and detail::max_frames_needed (line 1171); section 12; C3, C7
- **Severity:** major as reported, major after verification
- **Verdict:** partly

**Problem.** The fold-in answered audit findings 7 and 18 with one published number, max_shortfall, and sized steady<>'s FIFO (primed + max_outputs_for(block)) and fed_by's one-pull staging from it. Both derivations assume a stage's output never runs AHEAD of n L/M. The sketch's toy down2 emits on the second frame of a pair, so that holds there. The code the plan carries does the opposite: DspTap's decimator and SampleRateTap's rational ratio<1, M> stage emit output k as x[kM] arrives, so n inputs from reset give ceil(n/M) outputs. Such a stage has input_group M, never trails (cumulative shortfall 0) and leads by up to (M-1)/M of a frame; the mixed L/M stage leads too (it documents outputs_for(n) <= floor(nL/M) + 2). The contract has no member for a lead and the 3.2 definition is ambiguous between 'per call, from any state' and 'cumulative from reset' (the chain's second bound, 'one frame short of an input group', is justified cumulatively). Under either reading steady<> over the plan's own example shape (down by 2 then up by 2, e.g. 48 -> 24 -> 48 kHz around a block) overwrites unread frames, with every index in bounds and no audit check firing. Keeping the toy's floor alignment instead is not free: it changes the carried stages' latency and the bit-for-bit vectors C7 compares against.

**Recommendation.** Decide the alignment before C0b freezes stage_traits. - **Where:** D10; D49; section 3.2 ("fails with one static_assert per missing or ill-typed member"; reset row); section 3.3 ("asserts that a stage is trivially copyable and no larger than 256 bytes"); C0b (stage_traits, the default reset, the generic reset test); sketch.h lines 142-146, 848
- **Severity:** minor as reported, minor after verification
- **Verdict:** partly

**Problem.** (1) The reset probe asks whether `const Stage&` can call reset(state&). A stage whose author wrote reset without `const` (or by value, or private) has no such call, so it silently gets the default: zeros. For the sketch's gain that is a fade-in from 0 at every start, the very defect D49's own reset is there to prevent, and C0b's generic reset test (garbage then reset equals zeros then reset) passes, because both paths zero. (2) 3.2 says a missing member fails with catenae's static_assert; D10 says nothing probes for a member but reset. Both cannot hold: saying "missing" in catenae's words needs a detection per member (nine more probes). Without them the error is the compiler's own, which is readable. C0b's compile-fail battery has to expect one or the other. (3) "A chain is a stage", so it passes through stage_traits whenever it is nested (steady{gate}, parallel<ChainA, ChainB>, oversample). The sketch's chain keeps its configurations in std::tuple, which is not trivially copyable on libstdc++, and a chain's size is the sum of its stages': eleven second-order low-passes are 264 bytes, two order-16 Butterworth designs (about 170 bytes each by the response file) are 340. Both assertions fire on ordinary chains unless chains are exempted, which the plan does not say.

**Recommendation.** Close the probe's hole inside the trait: also detect any member named reset (`decltype(&T::reset)`), and static_assert that if one exists it is callable as reset(state&) on a const stage and is noexcept; or drop the probe and have a stage that rests at zero say so (`static constexpr bool rests_at_zero = true`), which also removes D10's exception and one deviation. Add to the generic harness a test that fails for a stage whose configuration matters at rest (output from reset differs between two configurations). Choose between D10 and 3.2 for missing members: the compiler's own error is adequate, so keep D10 and reword 3.2 to "one static_assert per ill-typed member". Say that the 256-byte ceiling is per leaf stage and that a chain's configuration is a recursive aggregate like its state, so that it is trivially copyable.

**Second reviewer.** (1) is finding 15, reproduced. (3) is finding 11, reproduced (the sketch's chain configuration is not trivially copyable). 'Cannot be written as stated' is overstated: the trivially-copyable and 256-byte assertions can be written and simply fire on a tuple-based chain, and a per-member presence check for a diagnostic is not what D10 forbids (D10 is about capabilities being inferred from members); at most 3.2 and D10 need one clarifying sentence.

### 22. The analyzer contract cannot count "since the last read" through a const state, and a chain gives no way to reach the tap's state

- **Lens:** paper (The contracts that exist only on paper, written as code)
- **Where:** Section 6.2 (result, results_ready rows; tap); section 4 (stage<I>() only); D34, D49; C0b (analyzer_traits), C1 (chain), C5
- **Severity:** minor as reported, minor after verification
- **Verdict:** confirmed

**Problem.** Under D34 an analyzer's result lives in its state, and 6.2 reads it with `result(const state&)` and `results_ready(const state&)`, "how many results have completed since the last read". Neither can record that a read happened, so results_ready as written can only be a running total. Two implementers will produce a total and a read that takes `state&`; analyzer_traits is frozen at C0b. Separately, the state the reader needs is the tap's part of the chain's state (and, behind fed_by, inside fed_by_state), and section 4 gives stage<I>() for a configuration but nothing for a stage's state. **Second reviewer.** Read 6.2: result(const state&) and results_ready(const state&) with 'since the last read' cannot record a read, and no other member does; section 4 offers stage<I>() for a configuration only, so the tap's part of the chain's state has no public accessor (the sketch reaches it through detail::item). ### 23. The junction table was not fully carried over to "configuration plus state": latency() takes no state, and a state holding atomics is not plain storage at C++20

- **Lens:** paper (The contracts that exist only on paper, written as code)
- **Where:** Section 6.1 (latency(), state, reset rows); D19 as amended; D2; section 7.3 ("Constructs to avoid ... a default-initialised std::atomic"); D45 (a junction over storage the caller supplies); C0b (junction_traits)
- **Severity:** minor as reported, minor after verification
- **Verdict:** confirmed

**Problem.** (1) 6.1 says latency() is callable from any thread and "for independent clocks it may change between calls", and also that a junction's configuration does not change while either side runs. After D19 everything that changes is in the state, so latency() with no state argument can only return configured numbers. The converter it is written for changes its target at run time from what its pulls observe and publishes it as an atomic in what will be the state. tolerance_ppm() and report() are right as written; latency() is the row that was missed. (2) The state row says "plain storage, as a stage's". With std::atomic members the type is trivially default constructible at C++17 and not at C++20 or 23 (the default constructor became value-initialising), so any assertion junction_traits takes over from stage_traits gives different answers across the three standards D2 requires to agree; 7.3 lists a default-initialised std::atomic among the constructs to avoid, and the junction state is exactly that by design. In storage a C caller supplies (D45), reset() stores into atomics that no constructor has run for; at C++20 std::atomic is not an implicit-lifetime type. The mailbox had the same point (second-audit findings 19 and 34) and got placement new and a deviation entry; the junction state, new in this commit, did not.

**Recommendation.** Write the row as `latency(const state&) const`, with handoff's returning its Target. In junction_traits assert only what holds at every standard (standard layout, trivially destructible, lock-free 32-bit atomics), not the stage's "plain aggregate" assertion. Have a junction's reset begin its atomics' lifetimes with placement new, as mailbox::post does, record it under the same deviation, and reword 7.3's list so that the junction state is the stated exception.

**Second reviewer.** (1) Read the 6.1 table: latency() takes no state yet 'may change between calls', while the configuration is fixed while either side runs; async's converter.h raises m_target_frames from the largest pull and publishes m_effective_target as an atomic (lines 351 to 357), which under D19 is state. (2) Measured: handoff::state is trivially default constructible at C++17 and not at C++20/23, and a static one gets start-up code at C++20 (relocation against s_relay); 7.3 lists a default-initialised std::atomic as a construct to avoid. One overstatement: the properties the plan actually asserts for a state (trivially copyable, standard layout) are equal at all three standards; the lifetime point in caller storage is unobservable.
